# humanize-ko — 자연스러운 한국어로 쓰고 다듬기

`humanizer-jp`의 핵심 아이디어를 한국어 글쓰기 workflow에 맞게 변형한 skill이다. 일본어 연구에서 확인된 수치와 표현 목록을 한국어에 그대로 적용하지 않는다. 한국어 규칙과 진단 결과는 문체를 점검하는 heuristic이며 AI 판별 점수가 아니다. 근거와 한계가 필요하면 [origin-and-limits.md](references/origin-and-limits.md)를 읽는다.

## 절대 바꾸지 않는 것

문체보다 내용의 무결성이 먼저다.

- 사실, 주장, 조건, 수치, 날짜, 가격과 범위를 유지한다.
- 인용문, 출처 link, code, 명령어, API 이름과 technical term을 보존한다.
- 제품을 사용했다거나 고객을 만났다는 경험을 새로 만들지 않는다.
- 불확실한 내용을 확신형으로 바꾸지 않는다.
- 원문의 출처나 AI 사용 사실을 숨기기 위한 문장을 만들지 않는다.
- 의도적인 오탈자, 비문, 과장된 감정, 뜬금없는 사담으로 사람인 척하지 않는다.

사실성과 문체가 충돌하면 사실성을 택한다.

## 새 글을 쓸 때

처음부터 다음 순서로 쓴다.

1. 독자가 검색한 문제와 글을 읽고 얻게 될 결과를 한 문장으로 고정한다.
2. 실제로 확인한 사실, 직접 재현한 결과, 가상 예시를 구분한다.
3. 매체와 말투를 정한다. 네이버 실용 글은 친절한 존댓말을 기본으로 하되 과한 친근함은 넣지 않는다.
4. 문제 상황에서 바로 시작한다. `이번 글에서는`, `지금부터 알아보겠습니다` 같은 예고는 특별한 이유가 없으면 생략한다.
5. 초안을 완성한 뒤 아래의 문단·문장·어휘 순서로 한 번 더 다듬는다.
6. 마지막에 CTA, 출처, 수치, code가 원래 의미와 같은지 대조한다.

## 기존 글을 다듬을 때

### 1. 문단의 역할부터 확인한다

각 문단에는 역할 하나만 둔다. 같은 내용을 소개, 요약, 결론에서 세 번 되풀이하면 한 곳만 남긴다. 반대로 긴 문단 안에 문제·원인·해결·예외가 모두 섞여 있으면 역할을 나눈다.

### 2. 문장 길이를 기계적으로 맞추지 않는다

짧은 문장만 같은 박자로 이어지면 두세 문장을 자연스럽게 묶는다. 긴 설명 뒤에는 결론을 짧게 둘 수 있다. 다만 수치를 맞추려고 체언 종결이나 한 단어 문장을 억지로 끼우지 않는다.

문장 길이의 목표값은 없다. 리듬은 글의 난도와 매체에 따라 달라진다.

### 3. 한국어 종결형의 연속 반복을 확인한다

존댓말 여부는 유지한다. `-합니다`, `-됩니다`, `-할 수 있습니다`가 여러 문장 연속으로 이어질 때만 문장 구조를 바꾼다. 말투를 바꾸기 위해 `-해요`, `-죠`를 무작정 섞지 않는다.

명사화도 줄인다.

- `확인하는 것이 중요합니다` → 무엇을 왜 확인해야 하는지 직접 쓴다.
- `활용할 수 있습니다` → 실제로 무엇을 할 수 있는지 쓴다.
- `진행을 하는 경우` → `진행하는 경우`

### 4. 상투적인 안내 문구를 걷어낸다

다음 표현은 금지어가 아니다. 내용 없이 자리를 채우거나 반복될 때 삭제하거나 구체화한다.

- `이번 글에서는`, `본 포스팅에서는`, `지금부터`
- `살펴보겠습니다`, `알아보겠습니다`, `정리해 보겠습니다`
- `먼저`, `다음으로`, `마지막으로`
- `또한`, `한편`, `따라서`, `즉`, `결론적으로`
- `효율적으로`, `효과적으로`, `다양한`, `강력한`
- `도움이 될 수 있습니다`, `활용할 수 있습니다`
- `~하는 것이 중요합니다`, `~라고 할 수 있습니다`
- `이상으로`, `도움이 되었기를 바랍니다`

접속사를 지운 뒤에도 관계가 분명하면 그대로 둔다. 관계가 모호해지면 더 정확한 접속어를 쓴다.

### 5. 평가 대신 관찰을 쓴다

`편리하다`, `강력하다`, `효율적이다`로 끝내지 않는다. 클릭 수, 소요 시간, 실패 조건, 전후 차이처럼 확인 가능한 근거가 있으면 그것을 쓴다. 근거가 없으면 평가 문장을 덜어낸다.

### 6. 구조는 독자에게 필요할 때만 쓴다

절차, 비교, checklist는 list와 table로 남긴다. 설명까지 전부 bullet로 만들지는 않는다. 한두 문장짜리 소제목이 연속하면 가까운 문단으로 합친다. 기술 글의 code block과 경고 callout은 가독성을 위해 유지한다.

## 진단 도구

초안이 길거나 리듬이 의심될 때 다음 script를 실행한다.

```bash
python3 <skill-dir>/scripts/humanize_ko_check.py <draft.md>
```

이 script는 다음만 보여준다.

- 문장 길이의 평균·범위·변동계수
- 비슷한 길이의 문장 네 개가 이어지는 구간
- 쉼표 없는 문장의 비율과 문장당 쉼표 수
- 같은 높임 종결형이 연속되는 최대 길이
- 한국어 상투 표현과 접속어의 출현 횟수

수치만 보고 자동 수정하지 않는다. 문제가 표시된 문단을 다시 읽고, 실제로 단조롭거나 모호할 때만 고친다.

## 최종 검수

- 첫 문단이 예고가 아니라 독자의 문제로 시작하는가?
- 긴 문장과 짧은 문장이 의미에 맞게 섞였는가?
- 같은 종결형과 접속어가 이유 없이 연속되는가?
- 추상적인 평가를 사실처럼 쓰지 않았는가?
- 가상 사례와 실제 경험을 구분했는가?
- code, 인용, 출처, 수치, CTA 조건이 바뀌지 않았는가?
- 소리 내어 읽었을 때 말투가 갑자기 달라지거나 숨이 막히는 문장이 있는가?

결과를 전달할 때는 자연스러움을 위해 고친 부분만 짧게 설명한다. 원문을 임의로 요약하거나 논지를 바꾸지 않는다.

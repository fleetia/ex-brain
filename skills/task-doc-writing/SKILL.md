# 작업 문서 작성 원칙

Notion의 태스크 문서 같은 작업 트래킹 문서는 한 직군만 보는 게 아니라 회사 전체가 읽는다. 이 skill은 그 문서를 쓰거나 고칠 때 적용하는 원칙이다.

## 적용 범위

- **적용**: 협업 도구의 태스크 문서, 진행 기록·결정 기록처럼 회사 공유용 작업 로그
- **적용 안 함**: 같은 직군끼리만 보는 전문 문서, 블로그·해설문(→ [cognitive-rhythm-writing](../cognitive-rhythm-writing/SKILL.md))

이 문서들은 원래 `[x]` 체크리스트와 날짜별 로그 나열 형식이라, [cognitive-rhythm-writing](../cognitive-rhythm-writing/SKILL.md)의 자체 기준으로도 "적용" 대상이 아니라 "진단 또는 제외"(작업 log, checklist) 대상이다. 리듬 장치를 억지로 넣지 말고 아래 원칙으로 평이하게 재구성한다.

## 원칙

1. **사실은 보존한다** — 날짜, 티켓/문서 번호, 결정 사항, 수치는 그대로 둔다.
2. **로그를 서술형으로 푼다** — `[x]` 체크리스트·항목 나열 대신 "무엇을 왜 했고 결과가 어땠는지"를 문단으로 재구성한다.
3. **전문 용어는 풀어 쓴다** — 다른 직군이 모를 법한 용어는 쉬운 말로 바꾸거나 괄호로 짧게 설명한다.
4. **사람 이름은 역할명으로** — 특정 인명 대신 디자이너, 담당자, PM 등 역할로 표현한다.
5. **불릿 하나에 사실 하나** — "제목 — 사실1, 사실2. 사실3"처럼 여러 사실을 대시(—)로 욱여넣지 않는다. 제목 불릿 + 중첩(nested) 하위 불릿으로 분리한다. 단, "—" 뒤에 딸린 사실이 하나뿐이면 굳이 중첩하지 않고 괄호나 한 문장으로 붙여도 된다.

예:
```
(X) 가이드 문서를 확장했습니다 — 빠른 시작 안내, 용어 표, 링크를 추가했습니다. 기존 표는 유지했습니다.

(O)
- 가이드를 처음 읽는 사람을 위한 문서로 확장했습니다
    - 빠른 시작 안내(설치부터 실행까지), 자주 쓰는 용어 표, 더 자세한 내용을 볼 수 있는 링크를 추가했습니다.
    - 기존 이름 규칙 표와 검증 절차 설명은 그대로 유지했습니다.
```

## 협업 도구에 실제로 반영할 때 주의할 것

- 여러 문서를 한 번에 고칠 계획이면, 먼저 초안을 사용자에게 보여주고 승인받은 뒤에 실제 페이지에 반영한다 (회사 전체 공유 문서라 되돌리기 번거로움).
- 부분 치환 방식으로 반영할 때는 도구가 본문을 저장하며 변형해 두었을 수 있다는 점을 주의한다 (예: Notion은 `README.md` 같은 파일명을 자동으로 링크로 바꿔놓아, 일반 텍스트로 치환을 시도하면 에러 없이 조용히 실패한다). 반영 전에 실제 저장된 본문을 먼저 읽어 정확한 형태로 치환하고, 반영 후 다시 읽어 누락이 없는지 확인한다.
- 여러 불릿이 큰 폭으로 바뀌는 문서는 부분 치환보다 전체 교체가 안전하다.

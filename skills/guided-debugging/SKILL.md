# 증상에서 원인까지 추적하기

오류 메시지를 없애는 데서 멈추지 않고, 사용자가 겪은 문제를 다시 만들고 실제 원인을 확인한다. 원인 설명 요청은 read-only로 다루고, "고쳐줘"처럼 수정을 요청했을 때만 local 파일을 바꾼다.

상위 지침이 언어를 정하지 않은 경우 사용자에게 보이는 질문·진행 상황·결과는 사용자가 지정한 언어를 우선하고, 없으면 최근의 의미 있는 사용자 발화 언어를 따른다. 발화가 짧거나 혼합되어 모호하면 이미 형성된 대화 언어를 유지하며, code·command·path·identifier와 원문 error message는 번역하지 않는다. 아래 결과 순서는 의미 구조이므로 선택한 응답 언어로 표현한다.

## 기대 동작과 실제 동작을 고정한다

- 사용자가 하려던 일, 기대한 결과, 실제로 본 결과를 각각 한 문장으로 정리한다.
- repository, 실행 화면, log, 기존 test에서 직접 확인할 수 있는 정보는 먼저 조사한다. 이미 알 수 있는 내용을 질문으로 되돌리지 않는다.
- test·start command와 repository script도 실행되는 code다. 실행 전에 직접 command뿐 아니라 이어서 호출되는 `pre*`·`post*` lifecycle script와 chained command까지 확인한다.
- 출처가 낯선 repository이거나 재현에 package install, network, 계정, secret, 실제 데이터 변경, 외부 전송이 필요하면 안전한 sample·local 격리를 먼저 찾고, 불가능할 때만 영향과 이유를 설명해 승인을 받는다. 오류 제보나 "고쳐줘"라는 요청을 이런 외부 효과의 포괄 승인으로 해석하지 않는다.
- 재현하지 못했다면 성공한 것처럼 넘기지 말고 확인한 조건과 부족한 증거를 구분한다.

## 전체 흐름에서 원인을 찾는다

증상이 보인 파일만 바로 고치지 않는다. 입력이나 사용자 동작에서 실제 출력까지 이어지는 data flow와 control flow를 추적한다.

- event·request → handler → state·data → renderer·response 순서에서 값이 어디서 달라지는지 확인한다.
- wrapper, switch, table cell, cache, build artifact처럼 아래 구현을 덮어쓰거나 오래된 결과를 보여줄 수 있는 경계를 확인한다.
- 정상 동작하는 가까운 흐름이 있으면 비교해 차이를 좁힌다.
- 관찰한 사실, 아직 검증하지 않은 가설, 확인한 root cause를 섞지 않는다.
- local 실행 오류는 source 수정 전에 dependency와 build 상태, project 고유 start command, 현재 설정을 먼저 확인한다.

## 원인을 소유한 곳만 고친다

수정 요청을 받았다면 확인한 root cause를 가장 가까이 소유한 지점에서 해결한다. caller마다 같은 guard를 흩뿌리거나, 문제와 무관한 cleanup·refactor·새 dependency를 함께 넣지 않는다. 사용자의 기존 변경과 데이터를 보존한다.

새 dependency, 파일·데이터 삭제, commit·push, deploy·publish, 외부 전송, 계정·실제 데이터 사용, 유료 자원 사용은 별도 승인 없이 실행하지 않는다.

## 처음 실패한 흐름으로 다시 확인한다

- 가능하면 수정 전에 실패하는 대표 test나 재현 절차를 먼저 확보한다.
- 수정 뒤에는 처음 실패한 사용 흐름과 root cause를 소유한 가장 가까운 test를 다시 확인한다.
- 관련 check를 마지막 변경 뒤 clean 상태로 다시 실행한다. 중간에 통과한 결과를 최종 검증으로 보고하지 않는다.
- 재현 환경이나 외부 상태 때문에 확인하지 못한 항목은 이유와 사용자가 확인할 가장 짧은 방법을 남긴다.

결과는 `겪었던 문제 → 확인한 원인 → 바꾼 내용 → 다시 확인한 범위 → 남은 불확실성` 순서로 쉬운 말로 설명한다.
